## 1. 프로젝트 한눈에 보기

### 무엇을 만드는가

집 안에 둔 휴대폰이 카메라로 넘어짐을 감지합니다. 영상은 휴대폰 밖으로 나가지 않고, 사람 형태만 남긴 실루엣 사진만 서버로 갑니다. 서버는 사고를 만들고 60초 동안 본인 응답을 기다린 뒤 가족에게 알립니다. 가족 한 명이 "제가 처리할게요"로 사고를 맡고, 119 신고는 **모의 기록**으로만 남습니다.

### 지금 상태 요약

| 항목 | 상태 |
|---|---|
| 전체 단계 | 핵심 흐름이 끝까지 이어진 **시연 가능 시제품**. 실사용 서비스는 아님 |
| 가장 잘 된 부분 | 사고 흐름 서버 코드와 자동 시험(서버 276개), 감지 규칙을 데이터로 찾고 검증한 과정 |
| 가장 부족한 부분 | **실제 휴대폰에서 한 번도 시험하지 못한 것**, 실제 문자·신고 없음, HTTPS 없음 |
| 가장 위험한 문제 | 이번에 재현한 **N-1**: 사고를 맡은 가족이 탈퇴하면 30분 뒤 서버 전체의 사고 타이머가 멈춤 |
| 알림을 보내는 규칙 | 옛 규칙. 새 규칙 v2는 **기록만** 하고 알림에 쓰이지 않음 |
| 운영 서버 | 2026-11-04 확인 시 **꺼져 있음**(8000번 포트 대기 없음). 이번 범위상 켜지 않았음 |

## 3. 현재 시스템 구성도 및 데이터 흐름

### 3-1. 구성 요소

```text
[감지 휴대폰 Android]                     [가족 휴대폰 Android/브라우저]
 CameraX → MediaPipe → 판정                Capacitor WebView = server/app/next
 실루엣 → DeviceLink                       FCM 푸시 수신 ← Firebase
      │ 기기 토큰(Bearer)                        │ 세션 쿠키
      ▼                                         ▼
[FastAPI 서버 server/main.py]  ── 매초 백그라운드 ── 사고 타이머·SMS(모의)·텔레그램·푸시·사진 정리
 accounts / people / devices / door_codes / incidents / alerts / push
      │
 [SQLite fall.db, WAL, 구조 12] [images/ 실루엣 JPG] [옛 흐름: events.json, residents.json]
      ▲
[PC 대시보드] 개발자 시험 도구. FD_DEV_DEVICES=1이거나 관리자 CLI 코드로만 연결
```

| 구성 요소 | 역할 | 연결 방식 |
|---|---|---|
| Android 앱 `mobile/` | 웹 화면 표시, 감지, 푸시 | 서버 URL을 WebView로 열고, 감지는 네이티브 서비스 |
| 웹앱 `server/app/next` | 모든 사용자 화면 | `/api/v2`, 5초 폴링(사고 중 2초) |
| FastAPI `server/` | 인증, 사고 판단, 알림 | SQLite 직접 접근 |
| PC `dashboard/`, `models/` | 개발 시험 | 기기 API, 미연결 시 옛 `/api/events` |
| 옛 `android/` | 미사용 첫 앱 | 빌드에 포함 안 됨 |
| 옛 화면 `/app/`, `/confirm`, `/`, `/reports` | 옛 흐름 | 공용 토큰 |

| 단계 | 구현 위치 | 상태 |

| 2. 낙상 판정 | `LegacyFallLogic`, 옆에서 `V2Shadow`는 로그만 | 연결됨. **v2는 알림과 끊겨 있음** |
| 3. 사고 이벤트 | `Silhouette.render` → `listener.onFall` | 연결됨. 렌더 예외 시 낙상 유실 (F2) |

### 3-3. 복잡하거나 유지보수가 어려운 부분

1. **알림 흐름 두 세대:** 옛 `main.py` 일부·`escalation`·`report119`·`notifiers`와 새 `incidents`·`alerts`·`push`가 공존합니다. 대기 시간(90초와 180초)도 다릅니다.
2. **규칙 사본:** 지금 방식은 PC 인라인, `fall_logic`, Java 3곳이고, `fall_detection.py`는 다른 규칙입니다. v2도 Python과 Java로 나뉩니다. 골든 시험이 일치를 지켜 주지만 고칠 곳이 많습니다.
3. **`store.js`의 mock·live 공존:** 규칙이 갈라져 mock 결과를 live 근거로 쓸 수 없습니다.
4. **전달 큐 3벌:** 문자, 텔레그램, 푸시의 재시도 코드가 거의 같습니다.
5. **연결 = 대상자 구조:** 집 연결, 감지 대상, 관리자가 묶여 있어 "부모 집을 등록하고 알림만 받는 보호자"를 표현하기 어렵습니다 (N-4).
6. **`main.py` 1,700줄:** 옛 라우트와 새 라우트가 한 파일에 있습니다.

- **가장 잘 구현된 부분:** 사고 상태 관리, 그리고 규칙을 학습용·시험용으로 나눠 한 번만 채점한 평가 방식입니다.
- **가장 부족한 부분:** 실제 폰 검증과, 감지 기기가 멈췄을 때 가족이 알 방법입니다.
- **가장 위험한 문제:** N-1입니다. 한 사람의 탈퇴로 **다른 가족의 낙상 알림까지** 멈춥니다. 안전 서비스에서 가장 나쁜 실패인 "조용한 실패"입니다. F3(분석 실패에도 "감지 중")도 같은 성격입니다.
- **지금 당장 개선할 부분:** N-1, N-5, F1, N-2, F2, F3입니다. (2026-11-04 모두 수정)
- **구조 변경이 필요한 곳:** 연결·대상자·관리자 분리(N-4), 옛 흐름 제거, 타이머 스레드 분리입니다. 서비스로 가려면 PC 서버를 클라우드로 옮겨야 합니다.
- **과제 결과물로 완성도를 높이려면:** 위 버그 수정, 시연 시나리오 고정, 깔끔한 첫 실행 환경, 현재 내용을 반영한 README, 평가 결과와 한계를 정직하게 담은 발표 자료가 필요합니다. 실제 폰 1대 시험이 가능해지면 가치가 가장 큽니다.
