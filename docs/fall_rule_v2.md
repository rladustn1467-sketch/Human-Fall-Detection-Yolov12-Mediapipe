# 낙상 판단 규칙 v2

작성: 2026-10-29. 코드: `fall_logic/v2.py` (`FallRuleV2`, `Params`), Java 이식 `V2Features.java`·`FallRuleV2.java` (아래). 기존 규칙(`fall_logic/legacy.py`, 앱의 `LegacyFallLogic`)은 그대로 두고 옆에 새로 만든 것.
아직 앱·PC 프로그램의 감지 흐름에 연결하지 않음 (평가용). 실제 휴대폰으로 확인하지 못한 항목은 아래 "미확인"에 따로 적음.

## 입력 (프레임마다, 주 인물 한 명)
관절 좌표를 **화면 픽셀**로 바꿔 계산한 값 (`tools/urfall_features.py`). 신뢰도 0.5 미만인 관절은 쓰지 않고, 사람이 없으면 모두 없음.

| 이름 | 뜻 |
|---|---|
| A1 | 어깨 중점 → 발목 중점 선이 수평과 이루는 각 (0° = 누움, 90° = 서 있음) |
| H3 | 머리(코)가 발목보다 얼마나 위인지, 몸통 길이 단위 (서 있으면 약 2~3, 바닥이면 약 0) |
| B1 | 사람 상자의 가로 ÷ 세로 |
| C1 | 엉덩이 중점이 0.25초 동안 내려간 속도, 몸통 길이/초 |

## 규칙
- **낮은 자세** = A1 < **40°** 또는 H3 < **0.3**
- **넓게 본 낮은 자세** = 낮은 자세 또는 B1 > **1.5**
- **(A) 빠르게 내려감**: C1 (앞뒤 프레임과 3개 중앙값으로 튀는 값 제거) ≥ **2.0** 몸통/초, 그 뒤 **1.0초** 안에 넓게 본 낮은 자세 **3프레임**
- **(B) 바닥에 있음 유지**: 넓게 본 낮은 자세가 **1.0초** 이상 이어짐. 사람이 안 보이는 1.0초 이하의 틈은 이어진 것으로 봄. 값이 있는데 넓게 본 낮은 자세가 아니면 끊김
- **낙상** = (A) 또는 (B)
- 평활 때문에 속도 판단은 한 프레임 늦음

(A)는 정면 카메라에서 넘어지는 순간을, (B)는 위에서 내려다보는 카메라와 천천히 넘어지는 경우를 맡음.
논문과의 관계: 시간 조건(ElderFallGuard p.4~5, Mali p.3의 20프레임 버퍼), 하강 속도(Chen p.7), 몸 선 각도(Ali p.95, Chen p.8), 상자 비율(Chen p.9, Omobot p.5), 머리-바닥 거리(Mali p.3, Ali p.94). 수치는 논문 것을 쓰지 않고 데이터로 새로 정함 (`docs/rules_from_papers.md`).

## 값을 정한 방법
- 데이터: UR Fall 61개 (영상 단위로 찾는 용 35 / 시험용 26) + CAUCAFall 100개 (사람 단위로 찾는 용 6명 60개 / 시험용 4명 40개). 안드로이드 방식 관절 (MediaPipe Pose Landmarker만)
- **찾는 용 영상만** 사용 (`tools/rule_search.py`, 조합 약 3만 9천 개)
- 원칙 (사용자 결정): 재현율 ≥ 90% 중 오탐이 가장 적은 조합. 엄격한 90%를 만족하는 조합이 없어 (최고 89.6%), **대안 1**로 결정: 넘어진 뒤 사람이 거의 안 보이는 낙상(넘어지기 시작 뒤 사람이 잡힌 프레임 30% 미만, 찾는 용 4개)을 뺀 "보이는 낙상"에서 재현율 ≥ 90%
- 찾는 용 결과: 재현율 40/48 (보이는 낙상 40/44 = 91%), 오탐 13/47 일상 영상. 같은 영상에서 지금 방식: 42/48, 오탐 35/47
- 실시간 코드(`FallRuleV2`)와 오프라인 검색은 찾는 용 95개 영상에서 판정이 모두 같음

## 알려진 한계
- 침대·소파에 눕기, 바닥에 일부러 엎드리기, (위에서 본) 의자 앉기·무릎 꿇기·줍기는 자세만으로 낙상과 구분이 어려워 오탐이 남음 → 앱의 60초 "괜찮아요" 확인이 한 번 거름. 장소 제외 구역 등은 다음 과제
- 사람을 찾지 못하면 어떤 규칙도 판단할 수 없음 (CAUCAFall 밤 적외선 + 얼굴 모자이크 영상)
- 카메라 쪽(앞뒤)으로 누우면 화면에서 세로로 보여 놓칠 수 있음
- 두 데이터셋 모두 연기한 낙상, 젊은 사람, 방 몇 곳. 실제 휴대폰 위치·노인·조명에서 다시 확인 필요
- 알림 뒤 다시 알리기(쿨다운), 일어난 뒤 초기화는 아직 정하지 않음 (지금은 처음 한 번만 알림)

## Java (안드로이드 앱) 이식
- 코드: `mobile/android/app/src/main/java/com/humanfall/app/detect/V2Features.java` (주 인물 고르기와 A1·H3·B1·C1 계산, `tools/urfall_features.py` 의 해당 부분),
  `FallRuleV2.java` (`fall_logic/v2.py`). 기본값 `FallRuleV2.Params.DEFAULT` = 위 규칙 값
- **아직 앱의 감지 흐름(`FallPipeline`)에는 연결하지 않음.** 앱은 지금도 `LegacyFallLogic` 으로 판단함
- 비교 시험 `FallRuleV2GoldenTest` (정답 파일: `tools/export_fall_v2_golden.py`)
  - 저장소에 넣은 작은 정답 파일: 8개 영상, 1,379프레임 (알림이 나는 영상 3개, 안 나는 영상 5개)
  - 전체 확인 (2026-10-29, 정답 파일은 저장소 밖, `FALL_V2_GOLDEN_ALL` 로 지정): **161개 영상 30,283프레임에서 프레임마다 A1·H3·B1·C1 이 모두 같고 (차이 ≤ 1e-9), 알림 93개와 알림 시각도 모두 같음**
  - 정답 값을 일부러 바꾸면 시험이 실패하는 것도 확인함
  - 입력의 관절 좌표는 소수 6자리로 줄여 저장. 줄이기 전후 Python 판정은 161개 영상 모두 같음

## 미확인 (실제 휴대폰이 있어야 확인할 수 있는 것)
위 결과는 모두 녹화된 데이터셋 영상을 PC 에서 안드로이드와 같은 방식으로 처리해 얻은 것이다. 아래는 확인하지 않았다.
- **미확인** 휴대폰 카메라의 실제 프레임 속도: 앱은 밀린 프레임을 버려서(KEEP_ONLY_LATEST) 간격이 일정하지 않다. C1 은 "0.25초 전 = 일정한 fps 로 몇 프레임 전"으로 계산하므로, 실제 휴대폰에서는 시각 기준으로 바꿔야 할 수 있음
- **미확인** 휴대폰의 MediaPipe(Android tasks-vision)와 PC 의 Python MediaPipe 가 같은 프레임에서 같은 관절을 내는지
- **미확인** 휴대폰을 실제로 두는 위치(높이·각도·거리)별 성능. 데이터셋은 사람 키 높이 정면(UR Fall)과 천장 모서리(CAUCAFall) 두 가지뿐
- **미확인** 실제 사용자(노인), 실제 집 조명·밤, 반려동물·여러 사람
- **미확인** 앱에 연결했을 때의 알림 흐름: 한 번 알린 뒤 다시 알리기(쿨다운), 일어난 뒤 초기화, 서버 사고·60초 확인과의 연결
- **미확인** 휴대폰의 처리 속도·발열·배터리 (규칙 계산은 프레임당 몇십 번의 덧셈·비교라 작을 것으로 예상하지만 재지 않음)
- **미확인** CAUCAFall 에서 사람을 못 찾은 원인(밤 적외선 + 얼굴 모자이크)이 실제 휴대폰 영상에서도 생기는지
