# 낙상 판단 규칙 v2

작성: 2026-10-29. 코드: `fall_logic/v2.py` (`FallRuleV2`, `Params`), Java 이식 `V2Features.java`·`FallRuleV2.java` (아래). 기존 규칙(`fall_logic/legacy.py`, 앱의 `LegacyFallLogic`)은 그대로 두고 옆에 새로 만든 것.
앱에는 **기록만 하는 방식**으로 연결함 (알림은 지금 방식이 계속 담당, 아래). PC 프로그램에는 연결하지 않음. 실제 휴대폰으로 확인하지 못한 항목은 아래 "미확인"에 따로 적음.

## 입력 (프레임마다, 주 인물 한 명)
관절 좌표를 **화면 픽셀**로 바꿔 계산한 값 (`tools/urfall_features.py`). 신뢰도 0.5 미만인 관절은 쓰지 않고, 사람이 없으면 모두 없음.

| 이름 | 뜻 |
|---|---|
| A1 | 어깨 중점 → 발목 중점 선이 수평과 이루는 각 (0° = 누움, 90° = 서 있음) |
| H3 | 머리(코)가 발목보다 얼마나 위인지, 몸통 길이 단위 (서 있으면 약 2~3, 바닥이면 약 0) |
| B1 | 사람 상자의 가로 ÷ 세로 |
| C1 | 엉덩이 중점이 0.25초 동안 내려간 속도, 몸통 길이/초. '0.25초 전'은 시각이 가장 가까운 프레임 (아래 "하강 속도를 시각으로") |

## 규칙
- **낮은 자세** = A1 < **40°** 또는 H3 < **0.3**
- **넓게 본 낮은 자세** = 낮은 자세 또는 B1 > **1.5**
- **(A) 빠르게 내려감**: C1 (앞뒤 프레임과 3개 중앙값으로 튀는 값 제거) ≥ **2.0** 몸통/초, 그 뒤 **1.0초** 안에 넓게 본 낮은 자세 **3프레임**
- **(B) 바닥에 있음 유지**: 넓게 본 낮은 자세가 **1.0초** 이상 이어짐. 사람이 안 보이는 1.0초 이하의 틈은 이어진 것으로 봄. 값이 있는데 넓게 본 낮은 자세가 아니면 끊김
- **낙상** = (A) 또는 (B)
- 평활 때문에 속도 판단은 한 프레임 늦음

(A)는 정면 카메라에서 넘어지는 순간을, (B)는 위에서 내려다보는 카메라와 천천히 넘어지는 경우를 맡음.
논문과의 관계: 시간 조건(ElderFallGuard p.4~5, Mali p.3의 20프레임 버퍼), 하강 속도(Chen p.7), 몸 선 각도(Ali p.95, Chen p.8), 상자 비율(Chen p.9, Omobot p.5), 머리-바닥 거리(Mali p.3, Ali p.94). 수치는 논문 것을 쓰지 않고 데이터로 새로 정함 (`docs/rules_from_papers.md`).

## 값을 정한 방법
- 데이터: UR Fall 61개 (영상 단위로 찾는 용 35 / 시험용 26) + CAUCAFall 100개 (사람 단위로 찾는 용 6명 60개 / 시험용 4명 40개). 안드로이드 방식 관절 (MediaPipe Pose Landmarker만)
- **찾는 용 영상만** 사용 (`tools/rule_search.py`, 조합 약 3만 9천 개)
- 원칙 (사용자 결정): 재현율 ≥ 90% 중 오탐이 가장 적은 조합. 엄격한 90%를 만족하는 조합이 없어 (최고 89.6%), **대안 1**로 결정: 넘어진 뒤 사람이 거의 안 보이는 낙상(넘어지기 시작 뒤 사람이 잡힌 프레임 30% 미만, 찾는 용 4개)을 뺀 "보이는 낙상"에서 재현율 ≥ 90%
- 찾는 용 결과: 재현율 40/48 (보이는 낙상 40/44 = 91%), 오탐 13/47 일상 영상. 같은 영상에서 지금 방식: 42/48, 오탐 35/47
- 실시간 코드(`FallRuleV2`)와 오프라인 검색은 찾는 용 95개 영상에서 판정이 모두 같음

## 알림 뒤 다시 판정 (사용자 결정 2026-10-29)
- **계속 누워 있는 동안은 다시 알리지 않음.** 휴대폰은 한 번만 보내고, 그 뒤 처리(60초 확인, 가족 알림, 단계별 진행)는 서버 사고가 맡음
- **일어난 뒤 초기화**: 알림 뒤 '넓게 본 낮은 자세'가 아닌 프레임이 **2초** 이어지면(사람이 안 보이는 1초 이하 틈은 이어진 것, 넓게 본 낮은 자세 프레임이 나오면 끊김) 규칙을 처음 상태로 되돌려 다시 판정할 수 있게 함. 사람이 안 보이는 동안은 초기화하지 않음
- **주 인물 한 명만** 판단 (값을 찾은 방식과 같음). 두 사람 중 작게 보이는 사람의 낙상은 놓칠 수 있음
- 코드: Python `fall_logic.v2.FallAlertsV2`, 앱 `FallAlertsV2.java` (규칙 `FallRuleV2` 자체는 그대로). 앱의 기록용 v2(`V2Shadow`)가 이것을 씀. 지금 방식의 알림(사람마다 5초 쿨다운)은 바꾸지 않음
- 시험: Python·Java 같은 5개 경우 (계속 누움 = 한 번, 2.3초 일어남 = 다시, 1.7초 = 다시 안 함, 안 보임 = 초기화 안 함·0.67초 틈은 이어짐). 정답 비교에 모든 알림 시각을 넣어 322개 경우 모두 같음. 녹화 영상에서 두 번 판정한 것은 일상 영상 2개 (이미 오탐이던 영상에서 일어났다가 다시 낮은 자세)

## 하강 속도를 시각으로 (2026-10-29)
휴대폰 카메라는 밀린 프레임을 버려서(KEEP_ONLY_LATEST) 프레임 간격이 일정하지 않다. 그래서 C1 의 '0.25초 전'을 프레임 수가 아니라 시각으로 찾도록 바꿈.
- 방법: 0.25초 전과 시각이 가장 가까운 프레임 (같은 거리면 더 이른 프레임), 0.1초 안에 없거나 시작한 지 0.25초가 안 됐으면 속도 없음. 두 프레임의 **실제 시간 차**로 나눔
- 코드: Python `tools/urfall_features.py` 의 `timing="time"` (`frame_seconds_before`), 앱 `V2Features`. 값을 찾을 때 쓴 프레임 수 방식(`timing="frames"`, 기본값)은 그대로 둠
- **고른 간격에서는 두 방식이 같음**: 161개 영상 전체에서 C1 차이 ≤ 4e-15, 판정 161개 모두 같음 → 위의 찾는 용·시험용 결과는 그대로 유효 (시험용은 다시 채점하지 않음)
- Java ↔ Python: 정답 비교에 프레임을 불규칙하게 뺀 경우를 더함. 161개 영상 × (전체 + 불규칙) = 322개, 45,200프레임에서 특징과 알림 168개가 모두 같음. 저장소의 작은 정답 파일은 11개(뺀 경우 3개)
- 에뮬레이터: UR Fall 6개를 '절반 속도, 간격 불규칙'으로 뺀 프레임만 넣어 실행 → 앱의 v2 판정 6개 모두 PC(같은 방식으로 뺀 기록)와 같음

### 프레임이 빠질 때 v2 (`tools/v2_uneven_frames.py`, 찾는 용 95개만)
| 버리는 방식 | 남은 프레임 | 프레임 수로 계산: 재현율 / 오탐 | 시각으로 계산: 재현율 / 오탐 |
|---|---|---|---|
| 전체 (고른 간격) | 100% | 40/48 / 13/47 | 40/48 / 13/47 |
| 하나 걸러 (절반 속도) | 50% | 37/48 / 11/47 | 35/48 / 9/47 |
| 절반 속도, 간격 불규칙 | 50% | 35/48 / 12/47 | 33/48 / 8/47 |
| 무작위 40% 버림 | 60% | 37/48 / 9/47 | 37/48 / 7/47 |
| 가끔 몇 프레임씩 멈춤 | 69% | 37/48 / 13/47 | 37/48 / 10/47 |

- 프레임 수로 세면 프레임이 빠졌을 때 실제보다 긴 시간을 0.25초로 보고 나눠서 **속도가 부풀려짐** (재현율이 조금 높아 보이지만 오탐도 늘어남). 시각으로 계산하면 속도는 맞음
- 그래도 **프레임이 절반으로 줄면 재현율이 40 → 33~35 로 떨어짐.** 원인은 (A) 빠른 하강: 하나 걸러 넣으면 (A)만으로 잡는 낙상이 23 → 14, (B) 바닥 유지는 30 → 29. 듬성듬성한 프레임에서는 3개 중앙값이 하강의 꼭대기 값을 지워 버림
- 즉 휴대폰에서 1초에 15장 이하로 처리되면 (A)가 약해짐. 실제 처리 속도를 잰 뒤 낮으면, 평활을 시간 기준으로 바꾸거나 그 속도의 영상으로 값을 다시 찾아야 함

## 미확인 (실제 휴대폰이 있어야 확인할 수 있는 것)
